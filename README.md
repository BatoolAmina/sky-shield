# AI-Enabled Drone & Counter-Drone Threat Simulation Trainer — SkyShield

An AI-enabled training simulator for drone and counter-drone threat scenarios: deterministic synthetic airspace and sensor simulation, a trained ML mentor with explainable assessments, an adaptive adversary, abstract countermeasure-response exercises, and a web app for trainees, instructors, and administrators. **Application code is plain JavaScript (ESM), no TypeScript, no build step for
the simulator, datagen or server.** The ML pipeline is Python (scikit-learn; optional PyTorch/LightGBM on your GPU).

> All data are **synthetic**, generated by the simulator in this repo. Results describe performance on that synthetic distribution and say nothing
> about real-world sensors. See `docs/LIMITATIONS.md`. Shipped results are in `results/v1/` (open `results/v1/REPORT.md`).

## What is inside

| Part | Where | What it does |
|---|---|---|
| Simulation core | `packages/sim-core/src` | Seeded deterministic world, 7 object classes, behaviours (state machines, boids swarm/flocks), radar/RF/EO/IFF sensors with clutter and shadowing, Kalman + alpha-beta tracker, fusion, feature extraction, response/ROE engine, scoring, Elo, after-action review, adaptive adversary (bandits), scripted defender |
| Mentor model runtime | `packages/sim-core/src/model` | Pure-JS inference for the exported tree model, calibration, **TreeSHAP written from scratch** (verified against brute-force Shapley values), template explanations |
| Dataset generator | `apps/datagen` | Headless generator: seed-wise train/val/test splits, shifted-distribution set, robustness sets, raw sequences, manifest |
| ML pipeline | `ml/src/skyshield_ml` | Audit/leakage tests, tuning, model zoo, calibration, threat threshold, evaluation, robustness, ablations, open-set, ranking, XAI, adversary plots, report |
| Server | `apps/server` | Auth (scrypt + JWT), roles, server-authoritative live sessions over WebSocket, REST API, MongoDB or in-memory/JSON store |
| Web app | `apps/web` | React + Vite + Tailwind CSS: responsive landing and account pages, tactical display, mentor panel with "Why?", response panel with ROE, review/replay with ground-truth overlay, instructor console |
| Results | `results/v1` | Metrics (JSON/CSV), 40+ figures, trained model, `REPORT.md` |

## Quick start

Requirements: **Node.js >= 20**, **Python >= 3.10**. (MongoDB optional.)

```bash
# 1. ML + simulation (everything: data -> models -> figures -> REPORT.md)
python -m venv .venv && source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r ml/requirements.txt                       # add torch (CUDA build) for the GPU module
python scripts/run_pipeline.py --quick                   # minutes; full run: python scripts/run_pipeline.py
# GPU sequence model (optional, needs PyTorch):
python scripts/run_pipeline.py --skip-datagen --with-gpu

# 2. Web app
npm install
```

Start each service in a separate terminal from the repository root:

```bash
# Terminal 1
npm run server
```

```bash
# Terminal 2
npm run web
```

Open `http://localhost:5173`. The frontend proxies REST and WebSocket requests to the server on port 4000.

Copy `.env.example` to `.env` in the repository root, then set a private `JWT_SECRET` and `INSTRUCTOR_CODE` before deploying. The server reads this file on startup. If `JWT_SECRET` is empty, it generates a temporary key and existing login sessions will expire when the server restarts.

### Vercel frontend deployment

Vercel can host the static React/Vite frontend, but the session backend must run on a persistent Node.js host that supports WebSockets. Import the repository using the root directory and the settings in `vercel.json`. Set `VITE_API_URL` in Vercel to the backend's HTTPS origin, then set `WEB_ORIGINS` on the backend to the exact Vercel frontend origin(s), including any preview origins you intend to use. Rebuild the frontend after setting `VITE_API_URL`. Configure MongoDB and the server secrets on the backend host; do not put server secrets in Vercel's frontend environment.

Google sign-in is optional. To enable it, create an OAuth **Web application** client in Google Cloud Console, add the app origin (for local development, `http://localhost:5173`) to its Authorized JavaScript origins, then put its client ID in the root `.env` as `GOOGLE_CLIENT_ID`. No client secret is used in the browser. The server validates Google's signed identity token, audience, issuer and verified-email claim before creating or signing into an account. Google sign-in is unavailable until this client ID is configured.

The server loads `results/v1/model/model.json` (the mentor). If it is missing the app still runs with the mentor disabled. Other settings: `PORT`, `ADMIN_CODE` (blank = admin sign-up disabled), `MONGO_URI` (otherwise `DATA_FILE` selects JSON persistence; blank uses in-memory storage), and `MODEL_PATH`.
Create an instructor account by registering with the instructor code, or an admin account with the admin code. Every account requires an email address and signs in with its username and password. The admin code is only for registration and is not a login credential. Trainee difficulty adapts to the Elo rating; the dashboard recommends a scenario for your rating.

Signed-in dashboards include a persistent dark/light theme switch in the top navigation. The theme applies across trainee, instructor, admin, session, and review screens.

## Role dashboards and live data

The signed-in home page is role-specific:

- **Trainee:** personal rating, completed runs, explored scenarios, rank and recent sessions from authenticated dashboard data.
- **Instructor:** live session observation, all-session analytics and recent run activity. Session changes are pushed over an authenticated WebSocket; a 15-second refresh is retained as a fallback.
- **Admin:** account/role management, landing-page copy editing, simulator scenario/event editing and platform analytics. Dashboard changes are pushed over the authenticated WebSocket with a 30-second fallback refresh.

Admin landing-page content and scenario edits are stored by the backend (in MongoDB or the configured JSON store) and are served to the public landing page and training clients. Scenario edits apply to newly created sessions; existing/running session records remain unchanged. New trainee accounts correctly start at rating 1000 with no personal completed runs; leaderboard placement is global. If `DATA_FILE` is unset and MongoDB is not configured, the server uses in-memory storage and data is lost on restart.

Trainee dashboard data is returned from one authenticated endpoint and refreshes on server events, with a 30-second fallback and a refresh when the tab regains focus. MongoDB startup creates indexes for account rating, user session history, session status and editable settings. The JSON fallback persists asynchronously so larger replay records do not synchronously block the Node event loop.

### Instructor-led training

The trainee starts a scenario from their own dashboard. Instructors then select that active run under **Live exercises** and open its live view to observe the synthetic tactical picture. They can send a short coaching note that appears immediately in the trainee's session, or adjust simulation conditions using the instructor controls. The trainee remains the session owner and makes the training decisions. Completed runs retain instructor notes for the trainee's after-action review; old sessions without notes show no coaching section.

## Design decisions worth knowing

* **Server-authoritative sessions.** The trainee's browser receives only the *perceived* picture (tracks, confidence, mentor output). Ground truth exists only on the server and in the after-action review. A test asserts that no truth fields leak.
* **Deterministic and replayable.** `(seed, scenario, action log)` reproduces a session exactly (tested). Each subsystem has its own PRNG stream, so adding a sensor draw never changes trajectories.
* **No leakage.** Splits are by scenario seed (windows of one scenario are correlated); calibration and the threat threshold use a separate validation split (valB) from tuning/early stopping (valA); the test set is touched once per final report; adversarial-validation, shuffled-label and range-only controls are run and reported.
* **Honest uncertainty.** Confidence intervals come from a cluster bootstrap over scenario seeds; model comparisons use paired tests.
* **Abstract response layer.** Warn / escalate / countermeasure / intercept are probabilities and delays only. Nothing weapon-specific is modelled.

## Retrain on your GPU

`python scripts/run_pipeline.py` regenerates everything from scratch. Install `lightgbm`, `xgboost`, `optuna` and PyTorch (CUDA) and they are picked up automatically
(LightGBM/XGBoost join the model comparison; Optuna replaces the built-in random search; `--with-gpu` adds the sequence network). The app always uses the exported
HistGradientBoosting tree model, because its JSON export is what the JavaScript runtime and TreeSHAP consume.
